# План проекта: cat

## 1. Цель

Написать на Си утилиту, повторяющую поведение GNU `cat`, чтобы освоить:
- работу с файлами и потоками (`fopen`, `fgetc`, `stdin`/`stdout`/`stderr`);
- разбор аргументов командной строки;
- сборку через `make` и организацию небольшого проекта на Си.

## 2. Требования

### Обязательно
- ✅ Вывод содержимого одного файла в stdout.
- ✅ Вывод нескольких файлов подряд, в порядке аргументов.
- ✅ Чтение из stdin, если файлы не переданы или передан аргумент `-`.
- ✅ Флаг `-n` — нумеровать все строки.
- ✅ Флаг `-b` — нумеровать только непустые строки (перекрывает `-n`).
- ✅ Флаг `-s` — схлопывать подряд идущие пустые строки в одну.
- ✅ Флаг `-E` — показывать `$` в конце каждой строки.
- ✅ Флаг `-T` — показывать табуляцию как `^I`.
- ✅ Флаг `--help` — вывести справку по использованию в stdout и завершиться с кодом 0.
- ✅ Ошибки (файл не найден, нет прав) — сообщение в stderr, продолжить со следующим файлом, код возврата 1.

### Если останется время
- ⬜ Длинные варианты флагов (`--number`, `--squeeze-blank` и т.д.).
- ⬜ Флаг `-A` (эквивалент `-vET`).
- ⬜ Флаг `-v` — отображение непечатаемых символов.

Статус: ⬜ не начат · 🔄 в работе · ✅ готово

Все обязательные требования выполнены: вывод совпадает с GNU `cat` на всех
тестовых файлах и комбинациях флагов, ошибки открытия не прерывают обработку
остальных файлов.

## 3. Границы (что НЕ делаем)

- Не поддерживаем локали и многобайтовые кодировки.
- Не оптимизируем скорость (никакого `mmap`, буферизации вручную).
- Не реализуем флаги, не перечисленные выше.
- Не поддерживаем `--` как признак конца опций: всё, что начинается с `-` и длиннее
  одного символа, разбирается как флаги. GNU `cat` такое принимает, мы — нет.

## 4. Технологии и инструменты

- Язык: C, стандарт C11.
- Компилятор: gcc, флаги `-Wall -Wextra -Werror -std=c11`.
- Сборка: `make`.
- Юнит-тесты: `minunit.h` (один заголовочный файл с макросами), тесты — обычные `.c` в `tests/`.
- Интеграционные тесты: bash-скрипт, сравнивающий вывод с системным `cat` на наборе файлов.
- Проверка памяти: `valgrind`.
- Форматирование: `clang-format` (стиль — на выбор, зафиксировать в `.clang-format`).

## 5. Архитектура

Поток выполнения:

```
argv → разбор флагов → для каждого файла:
                          открыть (или stdin) → читать побайтово (fgetc) →
                          применить флаги → вывести → закрыть
```

Чтение побайтовое, а не построчное (`fgets`): все флаги решаются на уровне
одного байта плюс небольшое состояние, которое переключается на каждом `\n`:

- `at_line_start` — в начале строки: для `-n` / `-b` печатаем номер;
- `prev_blank` — предыдущая строка была пустой: для `-s` пропускаем `\n`;
- байт `== '\n'` → для `-E` перед ним выводим `$`; байт `== '\t'` → для `-T` выводим `^I`.

Так нет ограничений на длину строки, нулевые байты выводятся как есть,
а файл без завершающего `\n` обрабатывается сам собой (нет `\n` — нет `$`
и нет номера у следующей строки).

Структура репозитория:

```
cat/
├── Makefile
├── README.md        — что за проект, сборка, запуск
├── .clang-format    — стиль кода для make cln / make cli
├── src/
│   ├── main.c       — только main(): вызывает разбор аргументов и обработку файлов
│   ├── args.c       — разбор аргументов командной строки, открытие входа
│   ├── args.h       — структура Options, объявления функций с контрактами
│   ├── cat.c        — логика вывода с учётом флагов
│   ├── cat.h        — структура CatState, объявление FileProcessing
│   └── my_errors.h  — внутренние коды ошибок
├── tests/
│   ├── README.md    — как устроено тестирование: два слоя, правила, ограничения
│   ├── minunit.h    — макросы для юнит-тестов
│   ├── test_args.c  — юнит-тесты разбора аргументов и открытия входа
│   ├── test_args.md — таблица реализованных тестов из test_args.c
│   ├── test_cat.c   — юнит-тесты логики вывода
│   ├── test_cat.md  — таблица реализованных тестов из test_cat.c
│   ├── run.sh       — интеграционные тесты: сравнение с /bin/cat
│   └── data/        — тестовые файлы (пустой, без \n в конце, с табами, с пустыми строками)
├── docs/
│   ├── plan.md      — этот файл
│   ├── structure.md — функции, структуры и их взаимосвязь
│   └── notes.md     — дневник разработки
└── build/           — объектные файлы, бинарник и тестовые бинарники (в .gitignore)
```

Правила, ради тестируемости:

- В `main.c` — только `main()`. Вся логика в `cat.c` / `args.c`, чтобы тестовый
  бинарник линковался с ними без `main.o`.
- Функции вывода принимают `FILE *out`, а не пишут в `stdout` напрямую —
  в тестах туда передаётся `tmpfile()` / `fmemopen()`.
- Разбор аргументов возвращает структуру опций, а не выставляет глобальные
  переменные — её удобно проверять в тестах.

Сборка тестов (`make test`):

```
build/cat       = main.o + args.o + cat.o
build/test_args = test_args.o + args.o + cat.o   (все объектники кроме main.o)
build/test_cat  = test_cat.o  + args.o + cat.o   (то же: LIB_OBJS в Makefile)
make test       → запуск test_args, test_cat, затем tests/run.sh;
                  все наборы прогоняются до конца, итог в конце
```

## 8. Решённые вопросы

- **Файл без завершающего `\n` при `-n` / `-E`.** Проверено на эталоне: `$` не
  добавляется, а следующий файл продолжает ту же строку и номера не получает.
  Отсюда `at_line_start` живёт в `CatState` и переживает вызов `FileProcessing`.
  Покрыто тестом `test_unfinished_line_continues`.
- **Бинарные файлы** — выводятся как есть. Побайтовое чтение через `fgetc`
  не портит ни нулевые байты, ни многобайтовые символы.
- **`getopt` или ручной разбор.** Выбран ручной: `ParseArgs` + `ParseFlags`.
  Для учебной цели полезнее, и позволяет своё поведение с `--` (см. «Границы»).
- **Тестирование stdin в юнит-тестах.** Оказалось возможным: `freopen` подменяет
  поток файлом, и тесты `CloseInput` проверяют сброс признака EOF. Поведение
  на настоящем терминале через пайпы не воспроизводится — проверяется вручную,
  инструкция в [tests/README.md](../tests/README.md).

## 9. Что осталось за рамками

Обязательная часть закончена. Мелочи, которые заметны, но на требования не влияют:

- Имя программы в сообщениях зашито как `cat`, GNU берёт его из `argv[0]`.
  Из-за этого `run.sh` приводит префиксы к общему виду через `sed`.
- Опечатка в имени `MEMMORY_ERROR` — лишняя `m`. Правка на два файла.
- Путь `MEMMORY_ERROR` не проверен тестом: неудачный `calloc` не воспроизвести
  без подмены аллокатора.
- Ошибки записи (`OUTPUT_ERROR`) проверяются вручную через `/dev/full`,
  автотеста нет — нужен поток, отказывающийся принимать данные.

Возможное продолжение — пункты из «Если останется время» в разделе 2:
длинные варианты флагов, `-v`, `-A`.
