# Тесты

```
make test
```

Прогоняются все наборы подряд, даже если какой-то упал; итог — в конце.
Запускать из корня проекта: тесты читают файлы из `data/` по относительным путям.

## Два слоя

| Слой | Где | Что проверяет | Эталон |
|------|-----|---------------|--------|
| Юнит-тесты | [test_args.c](test_args.c), [test_cat.c](test_cat.c) | отдельные функции | ожидаемые значения записаны в тесте |
| Интеграционные | [run.sh](run.sh) | программу целиком | системный `/bin/cat` |

Оба нужны, потому что видят разное. Юнит-тест `test_flags_unknown_short` проверяет,
что `ParseFlags` вернула код ошибки и напечатала нужный текст. Но он ничего не говорит
о том, что делает программа: интеграционная проверка `cat -z simple.txt` ловит,
что `main` не напечатал содержимое файла и вернул 1, а не 2 или 3.

Разбор тестов по файлам: [test_args.md](test_args.md).

## Правило эталона

В `run.sh` ожидаемый результат **никогда не пишется руками** — он берётся у системного
`cat`. Обе программы запускаются с одинаковыми аргументами, результаты сравниваются
побайтово: stdout, stderr и код возврата.

Отсюда следствие, о котором легко забыть: **намеренные отступления от GNU `cat`
в `run.sh` проверять нельзя.** Такой тест будет красным всегда, отражая не ошибку,
а решение из раздела «Границы» в [плане](../docs/plan.md).

Пример: `cat --number` GNU поддерживает (длинный вариант `-n`), а мы нет. Случай
проверяется юнит-тестом `test_flags_unknown_long`, а в `run.sh` для неизвестного
длинного флага взят `--number-all` — его не знает и GNU.

## Чего `run.sh` не может

**Поведение на терминале.** `cat - file -` с вводом, Ctrl+D, снова вводом работает
только на настоящем tty: EOF от терминала не окончательный, в отличие от EOF файла
или пайпа. Ради этого в `CloseInput` стоит `clearerr` — без него второй `-` ничего
не прочитает. Через пайпы такое не воспроизвести, нужен псевдотерминал.

Проверяется вручную:

```
./build/cat - tests/data/single_line.txt -
```

ввести текст, Ctrl+D, убедиться что показан файл, ввести ещё текст, Ctrl+D.
Каждая порция ввода должна отобразиться.

**Всё, что не отличает нас от GNU `cat`.** Внутренние коды ошибок, содержимое
структуры `Options`, освобождение памяти — это уровень юнит-тестов.

## Как добавить тесты

**Новый случай в `run.sh`** — одна строка:

```bash
check "$DATA/simple.txt" "$DATA/tabs.txt"    # обычные аргументы
check_stdin "$DATA/simple.txt" -             # с файлом на stdin
```

Ожидаемый результат писать не нужно, он берётся у эталона.

**Реализованный флаг** — дописать в переменную `FLAGS` в начале `run.sh`:

```bash
FLAGS="-n -b -s -E -T -nE -bs"
```

Он автоматически прогонится по всем файлам из `data/`, через stdin и в позиции
после имени файла.

**Новый юнит-тест** — функция в `test_args.c` или `test_cat.c`, объявление вверху
файла и строка `mu_run_test(...)` в `main`. Макросы — в [minunit.h](minunit.h).

**Новый файл тестов** — назвать `test_<что>.c`, и Makefile подхватит его сам:
цели собраны по маске `tests/test_*.c`. Тестовый бинарник линкуется со всеми
объектниками проекта, кроме `main.o` — поэтому в `main.c` не должно быть логики,
только вызовы.

## Данные

В [data/](data/) лежат маленькие файлы, каждый под свой случай: пустой, без `\n`
в конце, только переводы строк, с табами, с пустыми строками подряд, с кириллицей.
Они намеренно короткие — при расхождении diff читается глазами.

## Проверка памяти

Утечки и обращения за границы тесты не ловят, для этого отдельный прогон:

```
valgrind --leak-check=full ./build/test_args
make val
```

Тестовые бинарники стоит проверять на зелёном прогоне: при упавшем тесте
`mu_assert` выходит из функции мимо освобождения памяти, и valgrind покажет
утечку, которой в самой программе нет.
